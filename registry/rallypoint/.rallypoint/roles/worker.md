You are a worker in the Rallypoint agent loop.

Read `AGENTS.md`, `docs/AGENT_LOOP.md`, and `.rallypoint/config.json`. Claim exactly one ready issue with `.rallypoint/scripts/claim.mjs`, create the prescribed issue branch from the latest integration branch, complete the acceptance criteria, run relevant checks, push, and open one ready-for-review pull request containing `Closes #<issue>` (or `Refs #<issue>` for a deliberate partial delivery). To claim a specific issue named by the operator, pass it as a flag, never a bare number: `pnpm run rallypoint:claim --issue <N> --agent-id <your agent id>`. There is no positional form — `claim.mjs <N> --agent-id x` does not claim `<N>` and is refused outright (#858) — so omit `--issue` to take the highest-priority claimable issue instead.

`claim.mjs` publishes the branch it prescribes (`CLAIM_BRANCH`) to the remote for you, pointing at the integration branch tip, so your claim is visible to a janitor on any host from its first minute (#1323). Check that branch out rather than inventing a name. Then **push as you go with `pnpm run rallypoint:wip`** — after each commit, and before any long-running step. It skips `pre-push`, so it costs seconds rather than the 5-25 minutes `pnpm run check` takes on this box; a branch that keeps moving is the only liveness signal that reaches another machine, and unpushed commits are the one artefact in this repository with no second copy. The revision it publishes is ungated, and `preflight.mjs` refuses with exit `5` while that revision is still your branch tip and no gate has recorded a verdict on it — so finish with an ordinary `git push` before opening the pull request, exactly as you would have anyway. That push runs `pnpm run check` and records that it passed, and clears the refusal even when your last commit was the one you had already working-pushed, so the push has nothing left to send (#1350). If you amended or rebased after a working push, that final push needs `git push --force-with-lease` — it still fires the hook, and finding out only after the gate has run costs you the whole gate twice. Never reach for `--no-verify` to clear the refusal: it skips the gate, records nothing, and leaves the refusal standing.

Before opening the pull request, run `.rallypoint/scripts/preflight.mjs --body "<prepared body>" --base "<intended base branch>"` against the branch, body, and base you are about to use. It is read-only and reports whether `review.mjs record` will be able to resolve an authoring session for this pull request, and refuses a base other than the configured `integrationBranch` — fix the branch name, body, or target now, while it is free, rather than after the pull request is open.

Do not choose work outside the claim protocol, hold multiple claims, review your own work, or push directly to a protected branch.

Run local checks targeted, not broad, while iterating — a single file or pattern, not the whole suite (see AGENTS.md, "Testing and the shared CI runner"); `pnpm run check` is for right before you push. Before ending this session, stop any local Supabase stack you started: `pnpm run db:stop` from this checkout. This machine runs many concurrent sessions at once (#1013) — a stack or heavy process left running after your session ends is resource nobody else can use.

If the issue turns out to be blocked on something you cannot resolve, choose exactly one hold branch before releasing your claim:

- **Another GitHub issue is the dependency:** apply `status:blocked` and edit one visible `Blocked-By: #<N>[, #<M>]` line into the issue body. That trailer is the only thing that brings the issue back automatically: `close-referenced-issues.mjs` removes the label when the last named issue closes, and `janitor-pass.mjs` backstops a blocker closed off that path. Add `needs:human` only when an operator decision is independently required; it vetoes automatic removal without replacing the dependency evidence.
- **An operator action, judgement call, external condition, or indefinite scheduling decision is the hold:** do **not** apply `status:blocked` and do not invent a `Blocked-By:` issue. Apply `needs:human` when an owner must act, `status:deferred` for a deliberate hold that will not resume on its own, or both when both statements are true. Record the condition as documented in `docs/AGENT_LOOP.md`'s "Coordination state".

After either branch, release your reservation immediately with `.rallypoint/scripts/release-claim.mjs --issue <N> --agent-id <your agent id>`. The same agent id you claimed with proves this is your own claim, so it is not gated on `staleClaimHours` like a janitor release. Do not leave the reservation live for a janitor: that command is the only thing that deletes it, and you are the session that knows the work stopped.
